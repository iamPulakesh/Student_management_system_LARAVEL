How the Student Management System works

A plain-English walk through the codebase: what each part does, which file does it, and what happens under the hood when someone signs in, takes attendance or records marks. Each section starts with a one-line summary, then the details, then the real code.

01The app in 30 seconds

A web app where a college manages departments, courses, students, faculty, attendance and marks, with a separate portal for each kind of user.

Admin

Manages the master data: departments, courses, students and faculty (and their logins). Can review and correct attendance and marks.

Faculty

Sees only the courses they teach. Takes attendance for a whole class and records assessment marks.

Student

Sees their own courses, attendance history and marks. Can update their own contact details and password.

03MVC in plain English

MVC splits the app into three jobs: the Model knows the data, the View shows it, and the Controller decides what to do with a request.

An analogy you can use A restaurant. The controller is the waiter: takes your order and coordinates. The model is the kitchen and pantry: knows the ingredients and the recipes (the data and its rules). The view is the plate: how the food is presented. The waiter never cooks, and the kitchen never talks to the customer.

One real example: the admin opens the Students page

RouteThe URL /admin/students is matched.routes/web.php
ControllerReads the filters, asks the model for students.Admin/StudentController@index
ModelBuilds the database query, returns Student objects.app/Models/Student.php
ViewLoops over the students and prints the table.views/students/index.blade.php

The Controller: decides

It receives the request, asks models for data, and picks a view (or redirects). It does no HTML and no SQL itself.

Route::middleware(['auth', 'admin'])->prefix('admin')->name('admin.')->group(function () {
    Route::get('/dashboard', [AdminDashboardController::class, 'index'])->name('dashboard');
    Route::resource('students', StudentController::class);   // 7 CRUD routes in one line
    Route::resource('teachers', TeacherController::class);
    // ...departments, courses, attendance, assessments
});

// app/Http/Controllers/Admin/StudentController.php  (simplified)
public function index(Request $request): View
{
    $students = Student::query()
        ->with(['department', 'user'])                 // load related rows in one go
        ->where('department_id', $request->query('department_id'))
        ->orderBy('last_name')
        ->paginate(10);                                // 10 per page

    return view('students.index', ['students' => $students]);
}

The Model: knows the data

A model is a PHP class for one table. It knows its columns, its relationships (a student belongs to a department and has many attendance records) and small rules about itself. Laravel's Eloquent turns Student::query()->where(...)->get() into SQL for us.

// app/Models/Student.php
class Student extends Model
{
    protected $fillable = ['student_number', 'first_name', 'last_name', /* ... */];

    public function department(): BelongsTo { return $this->belongsTo(Department::class); }
    public function attendances(): HasMany  { return $this->hasMany(Attendance::class); }

    public function getFullNameAttribute(): string   // usable as $student->full_name
    {
        return trim("{$this->first_name} {$this->last_name}");
    }
}

The View: shows it

Blade templates are HTML with a few helpers: {{ }} prints a value (safely escaped), @foreach loops, @if branches. Views receive data from the controller and never query the database.

{{-- resources/views/students/index.blade.php (simplified) --}}
@foreach ($students as $student)
    <tr>
        <td>{{ $student->student_number }}</td>
        <td>{{ $student->full_name }}</td>
        <td>{{ $student->department?->name }}</td>
    </tr>
@endforeach

{{ $students->links() }}   {{-- pagination buttons --}}

Why this split is worth it

  • Easy to find things. A bug in a page layout? Look in the view. Wrong numbers? Look in the controller or model.
  • Reuse. The same Student model serves the admin list, the faculty roster and the student portal.
  • Safe changes. You can restyle every page without touching data logic, and vice versa.

Laravel adds two helpers around MVC that this app uses heavily: middleware (checks who you are before the controller runs) and Form Requests (checks what you sent before the controller runs). Both are explained below.

04Life of a request (under the hood)

Every click goes through the same pipeline. Each stage can stop the request early.

  1. The browser sends a request, e.g. POST /teacher/attendance with a form.
    public/index.php: the only entry point
  2. Laravel boots and loads the routes and middleware aliases.
    bootstrap/app.php
  3. Global clean-up: text fields are trimmed and empty fields become null, so validation sees clean input.
    Laravel's built-in TrimStrings, ConvertEmptyStringsToNull
  4. Web middleware: cookies are decrypted, the session is loaded from the sessions table, and the CSRF token is checked (forged form posts get HTTP 419).
    Laravel's built-in web middleware group
  5. Route matching: the URL and method pick a controller method.
    routes/web.php
  6. Route middleware: auth sends guests to the login page; admin / teacher / student return HTTP 403 for the wrong role.
    app/Http/Middleware/EnsureUserIs*.php
  7. Form Request (for forms): authorize() checks permission, rules() validates each field, after() runs cross-field checks. Any failure redirects back with error messages; the controller never runs.
    app/Http/Requests/*.php
  8. Controller does the work, using models (often inside a database transaction).
    app/Http/Controllers/**
  9. Response: either a Blade view is rendered to HTML, or a redirect is sent with a flash message ("Attendance recorded successfully.").
    resources/views/**
Key ideaBy the time a controller method runs, three things are already guaranteed: the user is signed in, they have the right role, and the input is valid. That's why the controllers are short.

Three design decisions worth explaining

Account vs. profile

Everyone logs in through users; the extra details sit in students or teachers. One login system for all roles, with role-specific data kept separate.

Enrolment is implicit

There's no enrolment table. A student is in a course when the department and semester match. Add a CSE Semester 3 student and they're instantly in every CSE Semester 3 course.

Nothing is orphaned

Every foreign key uses restrictOnDelete(): the database refuses to delete a row that other rows still point to. The controllers check first and show a friendly message.

// app/Models/Student.php
public function scopeEnrolledIn(Builder $query, Course $course): Builder
{
    return $query->where('department_id', $course->department_id)
        ->where('year_of_study', $course->semester);
}

// Used anywhere as:
$classList = Student::enrolledIn($course)->orderBy('student_number')->get();
// database/migrations/..._create_attendances_table.php
Schema::create('attendances', function (Blueprint $table) {
    $table->id();
    $table->foreignId('student_id')->constrained('students')->restrictOnDelete();
    $table->foreignId('course_id')->constrained('courses')->restrictOnDelete();
    $table->date('attendance_date')->index();
    $table->string('status', 20);
    $table->foreignId('recorded_by_user_id')->constrained('users')->restrictOnDelete();
    $table->timestamps();

    // one record per student, course and day: enforced by the database itself
    $table->unique(['student_id', 'course_id', 'attendance_date']);
});

06How accounts are created (“registration”)

There is no public sign-up page on purpose. Every account is created on the server, by someone already trusted, with the role set in code.

Why no self sign-up?In a college system you shouldn't be able to register yourself as faculty or admin. If the role came from a form, someone could edit the form and send role=admin. So the role is never accepted from user input at all.

What happens when the admin clicks “Create” on a new student

  1. Validation first. StoreStudentRequest checks the admin is an admin, the registration number is unique and alphanumeric, the email is real and unused, the password is 8+ characters, the phone is a valid mobile number, and so on.
    app/Http/Requests/StoreStudentRequest.php
  2. One transaction. Inside DB::transaction, the controller creates the users row with role student, then the students row pointing at it. If the second insert fails, the first is undone, so you never get a login without a profile.
    Admin/StudentController@store
  3. Password hashed automatically. The User model casts password as hashed, so it's stored as a bcrypt hash (12 rounds). The plain password is never saved.
    app/Models/User.php
  4. Redirect with a message. Back to the students list with “Student profile and login account created successfully.”
// app/Http/Controllers/Admin/StudentController.php
public function store(StoreStudentRequest $request): RedirectResponse
{
    $validated = $request->validated();   // only reaches here if validation passed

    DB::transaction(function () use ($validated): void {
        $user = User::createWithRole([
            'name' => "{$validated['first_name']} {$validated['last_name']}",
            'email' => $validated['email'],
            'password' => $validated['password'],      // hashed automatically
        ], User::ROLE_STUDENT);

        Student::create([/* reg no, name, phone, ... */ 'user_id' => $user->id]);
    });

    return redirect()->route('admin.students.index')
        ->with('success', 'Student profile and login account created successfully.');
}
// app/Models/User.php
public const ROLE_ADMIN = 'admin';
public const ROLE_TEACHER = 'teacher';
public const ROLE_STUDENT = 'student';

// 'role' is deliberately NOT here, so a form can never set it
protected $fillable = ['name', 'email', 'password'];

protected function casts(): array
{
    return ['password' => 'hashed'];   // always stored as a bcrypt hash
}

public static function createWithRole(array $attributes, string $role): self
{
    if (! in_array($role, self::ROLES, true)) {
        throw new \InvalidArgumentException("Invalid user role [{$role}].");
    }

    $user = new self([...]);   // name, email, password
    $user->role = $role;       // role is set explicitly, on the server only
    $user->save();

    return $user;
}

07How login works

One login page for everyone. You pick your role, and each role signs in with its own ID: registration number, employee code or email.

  1. The form. Choosing a role in the dropdown changes the label (Registration No / Employee Code / Email) with a few lines of JavaScript. The form posts to /login.
    resources/views/auth/login.blade.php
  2. Validate. Role must be one of the three; login ID and password are required.
    LoginController@store
  3. Rate limit. After 5 failed attempts for the same role + login ID + IP address, sign-in is locked for 60 seconds with a countdown message. This slows down password guessing.
    RateLimiter in LoginController
  4. Find the account. A student's registration number is looked up in students to find their user_id; a faculty employee code in teachers; an admin by email. IDs are upper-cased, emails lower-cased, so “f101” works.
    LoginController::attemptCredentials()
  5. Check the password. Auth::attempt() loads that user and compares the typed password against the stored bcrypt hash. Wrong → “Invalid Credentials.” and the failure is counted.
  6. Check the role matches. If a student's email was typed with “Admin” selected, the password may be right but the role isn't, so they're signed out again with “The selected role does not match this account.”
  7. Check the profile exists. A faculty or student login must have its profile row; otherwise it's refused.
  8. Start a fresh session. The session ID is regenerated (prevents session-fixation attacks), the failure counter is cleared, and the user is sent to their dashboard based on their role.
    User::dashboardRoute()
// app/Http/Controllers/Auth/LoginController.php  (store method, trimmed)
$credentials = $request->validate([
    'role' => ['required', 'string', Rule::in(User::ROLES)],
    'login_id' => ['required', 'string', 'max:255'],
    'password' => ['required', 'string'],
]);

if (RateLimiter::tooManyAttempts($throttleKey, self::MAX_FAILED_ATTEMPTS)) {   // 5 tries
    return $this->rejectLogin($request, 'login_id', "Too many sign-in attempts...");
}

$attemptCredentials = $this->attemptCredentials($credentials);

if ($attemptCredentials === null || ! Auth::attempt($attemptCredentials)) {
    RateLimiter::hit($throttleKey, self::LOCKOUT_SECONDS);                  // count the failure
    return $this->rejectLogin($request, 'login_id', 'Invalid Credentials.');
}

if ($user->role !== $credentials['role']) {
    return $this->rejectLogin($request, 'role', 'The selected role does not match this account.');
}

RateLimiter::clear($throttleKey);
$request->session()->regenerate();                      // new session ID after login
return redirect()->route($user->dashboardRoute());
// app/Http/Controllers/Auth/LoginController.php
private function attemptCredentials(array $credentials): ?array
{
    $loginId = trim($credentials['login_id']);

    if ($credentials['role'] === User::ROLE_ADMIN) {
        return ['email' => strtolower($loginId), 'password' => $credentials['password']];
    }

    $userId = $credentials['role'] === User::ROLE_STUDENT
        ? Student::query()->where('student_number', strtoupper($loginId))->value('user_id')
        : Teacher::query()->where('employee_number', strtoupper($loginId))->value('user_id');

    return $userId === null ? null : ['id' => $userId, 'password' => $credentials['password']];
}
// app/Models/User.php
public function dashboardRoute(): string
{
    return match ($this->role) {
        self::ROLE_ADMIN => 'admin.dashboard',
        self::ROLE_TEACHER => 'teacher.dashboard',
        default => 'student.dashboard',
    };
}

After login: how the app remembers you

Laravel stores the session in the sessions table and gives the browser an encrypted cookie with the session ID. On every request the auth middleware reads it, and $request->user() returns the signed-in User.

Logout

LoginController@destroy logs out, destroys the session, and issues a new CSRF token. The layout also forces a reload when a page is restored from the browser's back/forward cache, so pressing Back after signing out shows the login page, not a cached private page.

08How RBAC (role-based access control) works

Each user has exactly one role. Access is checked in layers: the role decides which portal you can open, and ownership decides which records inside it you can touch.

Layer 1: the role is stored safely

The users.role column holds admin, teacher or student. It's not mass-assignable and only User::createWithRole() sets it (see section 6).

Layer 2: route groups + role middleware

All routes for a portal sit in one group with two middleware: auth (must be signed in) and the role guard. A student who types /admin/dashboard gets 403 Access denied; the controller is never reached.

Route::middleware(['auth', 'admin'])->prefix('admin')->name('admin.')->group(function () {
    Route::get('/dashboard', [AdminDashboardController::class, 'index'])->name('dashboard');
    Route::resource('students', StudentController::class);   // 7 CRUD routes in one line
    Route::resource('teachers', TeacherController::class);
    // ...departments, courses, attendance, assessments
});

Route::middleware(['auth', 'teacher'])->prefix('teacher')->name('teacher.')->group(/* ... */);
Route::middleware(['auth', 'student'])->prefix('student')->name('student.')->group(/* ... */);
// bootstrap/app.php
->withMiddleware(function (Middleware $middleware): void {
    $middleware->alias([
        'admin' => EnsureUserIsAdmin::class,
        'teacher' => EnsureUserIsTeacher::class,
        'student' => EnsureUserIsStudent::class,
    ]);
})
// app/Http/Middleware/EnsureUserIsAdmin.php
public function handle(Request $request, Closure $next): Response
{
    $user = $request->user();

    if (! $user || ! $user->isAdmin()) {
        abort(403, 'Access denied. Administrator privileges are required.');
    }

    return $next($request);   // allowed: carry on to the controller
}

The teacher and student guards also require the linked profile ($user->teacher / $user->student) to exist.

Layer 3: ownership inside a portal

Being a faculty member isn't enough. You may only touch your own courses. Two places enforce this:

  • Form Requests check it in authorize() before saving anything (e.g. StoreAttendanceRequest, StoreAssessmentRequest).
  • Controllers check it when viewing (e.g. authorizeCourseAccess(), and Teacher/DashboardController@showCourse).
// app/Http/Controllers/Teacher/AttendanceController.php
private function authorizeCourseAccess(Request $request, Course $course): void
{
    $user = $request->user();

    if ($user->isAdmin()) {
        return;                                  // admins may see every course
    }

    $teacher = $user->teacher;
    if ($teacher === null || (int) $course->teacher_id !== (int) $teacher->id) {
        abort(403, 'You are not authorized to access attendance for this course.');
    }
}

Students are protected differently: their pages never take a student ID from the URL. The controller always loads the signed-in user's own profile, so there's no ID to tamper with.

// app/Http/Controllers/Student/DashboardController.php
private function resolveAuthorizedStudent(Request $request): Student
{
    // Always the signed-in user's own profile, never an ID taken from the URL.
    return $request->user()->student()->with(['department', 'user'])->firstOrFail();
}

09How the features work

Admin management (CRUD)

Students, faculty, departments and courses all follow the same Laravel “resource” pattern.

Route::resource('students', StudentController::class) creates seven routes: index (list), create (form), store (save), show (view one), edit (form), update (save changes), destroy (delete). Each form posts to a Form Request, and each list is paginated and loads related data in one query (with([...])) to avoid slow “N+1” queries.

  • Lists need a department filter first, so the admin never loads every row at once.
  • Deletes are guarded: a department with people or courses, a student with records, or a faculty member who teaches can't be deleted. You get a clear message instead.
  • Some fields lock once records exist: a student's or course's department and semester can't change after attendance or marks are recorded, because that would silently change who is enrolled.
  • Faculty only teach their own department: a course can only be assigned to faculty from the same department; the course form's dropdown filters itself to match.

Enrolment (who is in a course)

Computed on the fly with the enrolledIn scope from section 5: same department + semester. Used by the faculty roster, the attendance form, the marks form and the validation rules.

Taking attendance (faculty)

  1. Pick course and date on the Record Attendance page. The page loads the class list using enrolledIn, hiding anyone already marked for that day.
    AttendanceController@create · views/attendance/create.blade.php
  2. Everyone starts as Present; the teacher switches some to Absent and submits the whole class at once.
  3. Checks (StoreAttendanceRequest): it's their course; the date isn't in the future or more than 6 months ago; each status is present/absent; and every unmarked student in the class is included.
  4. Save as one batch inside a transaction. Each student is re-checked (enrolled? already marked?). If any check fails, nothing is saved, so you never get half a class.
  5. The database is the last guard: a unique index makes a duplicate (same student, course and date) impossible even if two people submit at once.
  6. Redirect to the attendance list showing each student's status and their percentage in that course (present ÷ total, highlighted green at 75% and above).
// app/Http/Requests/StoreAttendanceRequest.php  (shape of every Form Request)
class StoreAttendanceRequest extends FormRequest
{
    public function authorize(): bool      // 1. may this user do this at all?
    {
        // faculty only, and only for a course they teach
    }

    public function rules(): array         // 2. is each field valid?
    {
        return [
            'course_id' => ['required', 'integer', 'exists:courses,id'],
            'attendance_date' => ['required', 'date', 'before_or_equal:today',
                                  'after_or_equal:'.Attendance::earliestRecordableDate()],
            'statuses' => ['required', 'array', 'min:1'],
            'statuses.*' => ['required', Rule::in(['present', 'absent'])],
        ];
    }

    public function after(): array         // 3. checks that need several fields or the database
    {
        // every enrolled student who isn't marked yet must be in this batch
    }
}
// app/Http/Controllers/Teacher/AttendanceController.php  (store, trimmed)
DB::transaction(function () use ($validated, $course, $request) {
    foreach ($validated['statuses'] as $studentId => $status) {
        $student = Student::find((int) $studentId);

        if (! $student->isEnrolledIn($course)) {
            throw ValidationException::withMessages([...]);   // undo everything
        }

        if (/* already recorded for this date */) {
            throw ValidationException::withMessages([...]);
        }

        Attendance::create([
            'student_id' => $student->id,
            'course_id' => $course->id,
            'attendance_date' => $validated['attendance_date'],
            'status' => $status,
            'recorded_by_user_id' => $request->user()->id,     // who took it
        ]);
    }
});

Mistakes? Faculty can't overwrite a day once taken; they ask the admin, who can edit or delete single records (AttendanceController@edit/update/destroy).

Recording marks (faculty)

  • Pick course, student, assessment name (e.g. “Quiz 2”), date, marks obtained and maximum marks.
  • Rules: the student must be enrolled; marks can't be negative or above the maximum; the same assessment name can't be recorded twice for one student; and the first mark entered for “Quiz 2” in a course fixes its maximum (e.g. out of 20) for the whole class.
  • The percentage isn't stored. It's calculated whenever it's shown, by an accessor on the model.
// app/Http/Requests/StoreAssessmentRequest.php  (rules, trimmed)
'assessment_name' => ['required', 'string', 'max:150',
    Rule::unique('assessments', 'assessment_name')            // no duplicate "Quiz 1"
        ->where(fn ($q) => $q->where('student_id', $this->input('student_id'))
                             ->where('course_id', $this->input('course_id')))],
'marks_obtained' => ['required', 'integer', 'min:0', 'max:999', 'lte:max_marks'],
'max_marks'      => ['required', 'integer', 'gt:0', 'max:999'],
'assessment_date'=> ['required', 'date', 'before_or_equal:today', 'after_or_equal:...'],
// app/Models/Assessment.php
public function getPercentageAttribute(): float      // usable as $assessment->percentage
{
    $max = $this->max_marks;
    if ($max <= 0) {
        return 0.0;
    }

    return round(($this->marks_obtained / $max) * 100, 2);
}

The student portal

  • Dashboard: registration number, department, number of courses and overall attendance percentage, plus the profile.
  • Courses / Attendance / Assessments: read-only, always filtered to the signed-in student.
  • Update profile: only phone, date of birth, gender, address and password. Extra fields sent by a tampered form (department, name…) are ignored, because the controller only saves the validated safe fields. Changing the password requires the current password.

10Validation & data safety

Bad data is stopped in three places: in the browser (friendly hints), in Form Requests (the real check), and in the database (the final safety net).

Form Requests: one class per form

Each has authorize() (permission), rules() (field checks) and sometimes after() (checks that need several fields or the database). If anything fails, Laravel redirects back with the old input and the error under each field.

12Views & the UI

Server-rendered pages: one shared layout, small reusable pieces, one stylesheet, a little plain JavaScript.

  • Layout: layouts/app.blade.php holds the top bar, role-based menu and flash messages; every page @extends it and fills in @section('content').

14Questions developers may ask

Short answers you can give on the spot.

Why Form Requests instead of validating in the controller?
They keep controllers short, put permission and validation in one obvious place per form, and run before the controller, so a controller can trust its input. Rules shared by several forms live in one trait.
Why middleware for roles instead of checking inside each controller?
One check covers a whole group of routes, so it can't be forgotten on a new page. Ownership (which course) still needs a per-record check, which is done in Form Requests and controllers.
Why not Laravel Policies?
The rules are simple (one role per user, one owner per course), so middleware plus small ownership checks are clear enough. If permissions grew (e.g. heads of department), moving the ownership checks into Policies would be the natural next step.
Why is enrolment implicit? What about electives?
In this college model everyone in a department and semester takes the same courses, so there's nothing to manage: adding a student enrols them everywhere they belong. Electives would need an enrolments table; the enrolledIn scope is the single place to change.
How do you stop two teachers saving the same attendance at once?
Validation checks first, the save runs in a transaction, and a unique database index on student + course + date makes a duplicate impossible even in a race.
How do you avoid slow pages (N+1 queries)?
Related data is loaded up front with with(['department', 'user']), counts use withCount(), and lists are paginated.
Where are passwords stored and how?
In users.password, as a bcrypt hash (12 rounds) via Laravel's hashed cast. Login compares hashes with Auth::attempt(); the plain password is never stored.
Why can't a student register themselves?
Student and faculty records are official data owned by the college, and roles must never come from user input. The admin creates accounts; the first admin comes from the app:create-admin command.
Why does every attendance and mark record store who recorded it?
Accountability. recorded_by_user_id shows who took the attendance, and who entered or last edited a mark. It appears in the “Recorded By” column on the attendance and marks lists.

15Honest limitations

Worth saying before someone else does. Each is a clear next step.

  • No automated tests yet. Features and validation were checked by sending real requests, but there's no PHPUnit/Pest suite. Adding feature tests is the first improvement.
  • No “forgot password”. The admin resets passwords from the edit form.
  • Implicit enrolment can't model electives or repeat students (see Q&A).
  • Vite isn't used. vite.config.js is the Laravel default; the pages load public/css/app.css directly.
  • Timestamps before the timezone change (created_at) were saved in UTC; dates of attendance and marks are unaffected.
